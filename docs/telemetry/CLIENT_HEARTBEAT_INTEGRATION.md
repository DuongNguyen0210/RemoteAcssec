# Client Heartbeat Integration Contract

**Scope:** basic device heartbeat / online reporting.
**This is NOT CPU / RAM / GPU / FPS telemetry.** No performance metric is collected, sent, or
stored in this phase.

This document only describes the **API that already exists in the server source**. It is not a new
protocol and it does not define anything the server does not currently implement. The C++/Qt client
must implement against exactly this contract.

---

## 1. Management API runtime configuration

Derived from `server/management-api/src/main/resources/application.yml`:

| Setting | Value | Source |
| --- | --- | --- |
| HTTP port | `9090` | `server.port` |
| Application name | `management-api` | `spring.application.name` |
| Database | PostgreSQL `remote_db` @ `localhost:5432` | `spring.datasource.url` |
| Redis | `localhost:6379` | `spring.data.redis` |

Base URL for local development:

```
http://localhost:9090
```

Health probe (already implemented in `HealthController`):

```
GET http://localhost:9090/api/v1/health   ->  200  {"status":"UP","service":"management-api"}
```

> **Note — heartbeat does NOT go through the Relay.**
> The relay-proxy (`RelayServer.main`, hard-coded port `8080`) speaks the binary RDTP protocol and
> has no heartbeat handling. Heartbeat is plain HTTP/JSON straight to the Management API on `9090`.

> **Known configuration mismatch (reported, not changed).**
> `infrastructure/nginx.conf` assumes `management-api:8080` and `relay-proxy-*:9090` — the two ports
> are swapped relative to the runtime source (`application.yml` = 9090, `RelayServer` = 8080).
> The client must follow the **runtime source**, i.e. port `9090` for the Management API.

## 2. Endpoint

```
POST /api/v1/devices/heartbeat
```

Full URL:

```
POST http://<management-api-host>:9090/api/v1/devices/heartbeat
```

Headers:

```
Content-Type: application/json
```

No authentication header is required in this phase (no JWT, no session token).

---

## 3. Request fields

Exactly the fields of the current `HeartbeatRequest` DTO
(`server/management-api/src/main/java/com/remotecontrol/api/dto/HeartbeatRequest.java`):

| Field | Type | Required | Validation | Meaning / server handling |
| --- | --- | --- | --- | --- |
| `deviceUid` | string | **yes** | `@NotBlank` | Stable device identifier generated by the client. **Currently logged only — not persisted** (no matching column on the `Child` entity). |
| `name` | string | **yes** | `@NotBlank` | Human-readable device/machine name. Written to `child.name`. |
| `username` | string | **yes** | `@NotBlank` | **Device identity.** Must equal the `child_username` of the child account the client logged in with (the account that returned `role: "CHILD"` from `POST /api/v1/auth/login`). Used to look up the device row. |
| `ipAddress` | string | no | — | Written to `child.ip_address`. If omitted / empty, the server substitutes the TCP remote address of the request (`HttpServletRequest.getRemoteAddr()`), so the client may leave it out. |

No other field is accepted or read. Do **not** send `cpu`, `ram`, `gpu`, `fps`, `bandwidth`,
`sessionId`, or `token` — they are not part of the DTO in this phase.

### Example request

```http
POST /api/v1/devices/heartbeat HTTP/1.1
Host: localhost:9090
Content-Type: application/json

{
  "deviceUid": "UID-ABC-123",
  "name": "Phong-Khach-PC",
  "username": "child_pc01",
  "ipAddress": "192.168.1.50"
}
```

Minimal valid request (server fills in the IP):

```json
{
  "deviceUid": "UID-ABC-123",
  "name": "Phong-Khach-PC",
  "username": "child_pc01"
}
```

## 4. Prerequisite: the device must already exist

Heartbeat **only updates** an existing device. It never creates accounts.

The `child` row must already exist (created by the parent/admin account) with
`child_username` equal to the `username` sent in the heartbeat. This is because `child.user_id`
(owner) is `NOT NULL` and the heartbeat request carries no owner information that could be resolved
safely.

Consequence for the client: heartbeat should only be started **after a successful login** that
returned `role: "CHILD"`.

---

## 5. Success response

Actual current implementation (`DeviceController.heartbeat`):

```
HTTP/1.1 200 OK
Content-Type: text/plain;charset=UTF-8

OK
```

Body is the literal plain-text string `OK`. There is no JSON envelope.

Server-side effect on the matched `child` row (`DeviceService.processHeartbeat`):

| Column | New value |
| --- | --- |
| `name` | `request.name` |
| `ip_address` | `request.ipAddress` (only if non-blank) |
| `status` | `"ONLINE"` |
| `last_seen` | server time, `LocalDateTime.now()` |

The client should treat any `2xx` as success and simply wait for the next tick.

---

## 6. Failure responses

Actual current behaviour:

### 6.1 Unknown device — `404 Not Found`

Returned when no `child` row has `child_username = username`.

```
HTTP/1.1 404 Not Found
Content-Type: text/plain;charset=UTF-8

DEVICE_NOT_FOUND
```

Nothing is written to the database. The server logs a warning. **No user or device account is
created.**

Recommended client behaviour: stop the heartbeat timer and surface a "device not registered"
state — retrying will not help until the account is provisioned.

### 6.2 Validation error — `400 Bad Request`

Returned by Spring's default validation handling when `deviceUid`, `name`, or `username` is
missing, `null`, empty, or whitespace-only.

```
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "timestamp": "2026-08-28T03:01:01.398+00:00",
  "status": 400,
  "error": "Bad Request",
  "path": "/api/v1/devices/heartbeat"
}
```

Recommended client behaviour: this is a client bug — log it, do not retry with the same payload.

### 6.3 Server / network unreachable

No response, connection refused, or `5xx`. Recommended client behaviour: keep the timer running and
retry on the next tick.

---

## 7. Recommended client reporting interval

```
5000 ms
```

The client should send one heartbeat every **5000 ms** while it is logged in. The server does not
enforce or advertise an interval, and there is currently no server-side offline sweep — nothing
flips `status` back to `OFFLINE` automatically in this phase.

---

## 8. Summary of what is and is not covered

Covered:

- Device reports "I am online" every 5 s over HTTP/JSON.
- Server refreshes `name`, `ip_address`, `status`, `last_seen` for a known device.

Not covered in this phase:

- CPU / RAM / GPU / FPS / bandwidth telemetry
- Relay / RDTP transport for heartbeat
- Redis heartbeat pipeline
- Persistence of `deviceUid`
- Automatic `OFFLINE` transition after missed heartbeats
- Authentication of the heartbeat call (no JWT / token)
- Session management, screen capture, streaming, input forwarding
